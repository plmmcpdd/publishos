# PublishOS — 实施路线图

## 项目概览

- **目标**：社交媒体代运营合规发布系统 v1.0（TikTok-first）
- **工期**：6 周（乐观）/ 8-10 周（现实，含平台审核等待）
- **团队**：外部开发团队（Codex + 人工 review）
- **关键里程碑**：M1（技术验证）→ M2（MVP 可用）→ M3（内测）→ M4（上线）

## 里程碑

### M1 — 技术验证与脚手架（Week 1）

**目标：** 确认核心技术可行性，搭建开发环境，锁定架构决策。

| 任务 | 负责人 | 工期 | 验收标准 |
|------|--------|------|----------|
| TikTok 网页版自动化发布验证 | 外部团队 | 5 天 | 能稳定完成：登录→上传→填文案→发布，连续 30 天无风控触发 |
| AWS 美国账户开户 | @gid T | 3-5 天 | 账户可登录，可创建 EC2/RDS/S3 资源 |
| 后端脚手架搭建（Node/Prisma/Express） | 外部团队 | 3 天 | `npm run dev` 启动，数据库迁移成功 |
| Electron 桌面端原型 | 外部团队 | 3 天 | 能显示三屏 Tab，能弹出系统通知 |
| 设计稿定稿（warm 方向） | @设计师 | 2 天 | 客户端 + 后台两版完整设计稿 |

**M1 风险：**
- 🔴 **TikTok 自动化验证失败** → 降级为「一键导出 + 客户手动上传」，工期缩短至 4 周
- 🔴 **AWS 开户延迟** → 开发用本地 Docker 模拟，部署延后

---

### M2 — MVP 核心链路（Week 2-3）

**目标：** 内容创建 → 审核 → 客户端队列 → 发布 → 状态回传 全链路跑通。

| 任务 | 负责人 | 工期 | 依赖 |
|------|--------|------|------|
| 内容创建 API（中国团队上传） | 外部团队 | 3 天 | M1 脚手架 |
| 审核网关（Approve/Reject） | 外部团队 | 2 天 | M1 脚手架 |
| 客户端队列拉取 + 设备认证 | 外部团队 | 3 天 | M1 原型 |
| 客户端确认发布 → 浏览器唤起 | 外部团队 | 4 天 | M1 自动化验证通过 |
| 状态回传 + 审计日志 | 外部团队 | 2 天 | M1 脚手架 |
| 运营后台 Dashboard（基础版） | 外部团队 | 4 天 | M1 设计稿 |
| AI 披露标签自动配置 | 外部团队 | 2 天 | M1 设计稿 |
| S3 预签名 URL + 素材存储 | 外部团队 | 2 天 | AWS 账户 |
| 数据库模型 + 迁移 | 外部团队 | 2 天 | M1 脚手架 |

**M2 风险：**
- 🟡 **TikTok 自动化不稳定** → 需要真实账号 + 真实环境持续测试，不能靠开发环境 spike
- 🟡 **Meta Graph API 审核延迟**（Instagram P1）→ Instagram 延后到 v2

---

### M3 — 内测与合规加固（Week 4-5）

**目标：** 找 2-3 个早期客户试用，发现并修复问题，合规层完整落地。

| 任务 | 负责人 | 工期 | 说明 |
|------|--------|------|------|
| 内测客户招募 | @gid T | 持续 | 找 2-3 个现有客户，免费试用 + 反馈 |
| 客户端安装包分发（Win/Mac） | 外部团队 | 2 天 | Electron 打包 + 签名 + 自动更新 |
| 运营后台权限系统（RBAC） | 外部团队 | 3 天 | 中国团队 / 美国运营 / 管理员 三角色 |
| 合规自动化层完整落地 | 外部团队 | 3 天 | License Missing 阻断 + 蓝领广告用语检测 |
| 账号健康监控（shadowban 检测） | 外部团队 | 3 天 | 每日扫描 + 告警通知 |
| 错误处理 + 日志系统 | 外部团队 | 2 天 | Sentry 或自建，客户端崩溃收集 |
| 性能优化（启动时间 < 3s） | 外部团队 | 2 天 | 客户端优化 |
| 内测反馈收集与修复 | 外部团队 | 持续 | 按优先级修复 |

**M3 风险：**
- 🟡 **内测客户不配合** → 延长内测期或降低客户数要求
- 🟡 **shadowban 检测准确率不足** → 依赖第三方工具或自建 heuristics

---

### M4 — 上线与运维（Week 6）

**目标：** 正式对付费客户开放，建立运维和监控体系。

| 任务 | 负责人 | 工期 | 说明 |
|------|--------|------|------|
| 生产环境部署（AWS VPC） | 外部团队 | 2 天 | 需要 AWS 美国账户 |
| 域名 + HTTPS 证书 | 外部团队 | 1 天 | 建议用 Cloudflare |
| 监控告警（Uptime / Error Rate） | 外部团队 | 2 天 | 建议用 Datadog 或 CloudWatch |
| 备份策略（数据库 + 素材） | 外部团队 | 1 天 | 每日自动备份 |
| 运维手册 | 外部团队 | 1 天 | 故障处理、回滚、升级流程 |
| 客户 onboarding 文档 | 我 / @设计师 | 2 天 | 安装指南、使用教程、FAQ |
| 上线公告 + 客户通知 | @gid T | 1 天 | 邮件/微信通知现有客户 |

**M4 风险：**
- 🟡 **AWS 美国账户延迟** → 部署用中国区 AWS 临时过渡（合规风险高，不建议）

## 并行工作流

```
Week 1:  [TikTok验证]  [AWS开户]  [脚手架]  [原型]  [设计稿]
Week 2:  [API开发]  [客户端开发]  [后台开发]  [测试]
Week 3:  [API开发]  [客户端开发]  [后台开发]  [测试]
Week 4:  [内测]  [合规加固]  [打包分发]  [反馈修复]
Week 5:  [内测]  [合规加固]  [监控]  [反馈修复]
Week 6:  [部署]  [运维]  [上线]
```

## 关键路径

**最长路径（决定总工期）：**
TikTok 自动化验证（Week 1，5 天）→ 客户端发布链路（Week 2-3，7 天）→ 内测修复（Week 4-5，10 天）→ 部署上线（Week 6，2 天）= **6 周（乐观）**

**若 TikTok 自动化验证失败 → 降级方案：**
- 客户端改为「一键导出 + 客户手动上传」
- 客户端开发减少 2 天（不需要浏览器唤起自动化）
- 总工期：4 周
